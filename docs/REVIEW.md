# Крос-рев'ю, лабораторна №12 (структурні шаблони: Flyweight, Composite, Bridge)

Розподіл: Катя реалізувала Завдання 1-2 (Flyweight, Composite), Стас реалізував Завдання 3 (Bridge).
Рецензенти: Стас перевіряє Завдання 1-2, Катя перевіряє Завдання 3.

Критерії (з умови): діаграма відповідає коду; рішення усуває проблему з опису; раннер відтворює демонстраційний сценарій; для ситуацій з великою кількістю об'єктів виводиться кількість фактично створених об'єктів.

## Завдання 1. Flyweight (рецензент: Стас)

| Критерій | Що перевірено | Результат |
|---|---|---|
| Діаграма відповідає коду | `CarModel` (Flyweight), `CarModelFactory` (Flyweight Factory) зі словником `_models` і `GetModel`, `MapMarker` (Context) з посиланням на модель | ☐ |
| Рішення усуває проблему | Дані моделі зберігаються один раз; позначка тримає лише номер, координати, час; повторний запит моделі не створює новий об'єкт (перевірено `ReferenceEquals`) | ☐ |
| Раннер відтворює сценарій | 100 000 позначок для 4 моделей; виведено кількість позначок і моделей (4); дві позначки різних авто однієї моделі посилаються на один об'єкт | ☐ |
| Виведено кількість створених об'єктів | Рядки `Позначок: 100000` і `Об'єктів моделей: 4`, плюс 4 записи про створення моделі від фабрики | ☐ |

| № | Зауваження | Статус |
|---|---|---|
| 1 | `CarModel` незмінний (лише get), тому безпечно ділиться між тисячами позначок | ☐ прийнято |
| 2 | `CarModelFactory` не потокобезпечна (звичайний `Dictionary`); для консольного демо прийнятно, у захисті згадати `ConcurrentDictionary` | ☐ прийнято |

## Завдання 2. Composite (рецензент: Стас)

| Критерій | Що перевірено | Результат |
|---|---|---|
| Діаграма відповідає коду | `IZoneComponent` (Component), `ParkingLot` (Leaf), `Zone` (Composite) зі списком дітей `_children`, `ZoneAnalytics` (Client) | ☐ |
| Рішення усуває проблему | Майданчик і зона обробляються через один інтерфейс; кількість авто й виручка рахуються рекурсією на будь-якій глибині; бізнес-центр у кварталі це `Zone`; аналітика не змінюється при новому рівні | ☐ |
| Раннер відтворює сценарій | Структура місто → райони → квартали → бізнес-центр → майданчики; дерево з показниками кожного вузла; `Report` для міста й району тим самим викликом | ☐ |
| Контрольні числа | Місто 58 авто і 89400 грн; Шевченківський 35 і 57200; квартал «Центр» 25 і 42700; БЦ Ренесанс 13 і 24300; Садгірський 23 і 32200 | ☐ |

| № | Зауваження | Статус |
|---|---|---|
| 1 | Зв'язок `Zone` з дітьми показано агрегацією; діти не існують окремо від дерева, тож на захисті можна обґрунтувати й композицію | ☐ прийнято |
| 2 | `GetCarCount` і `GetRevenue` перераховуються для кожного вузла при виведенні дерева; для невеликої структури не проблема | ☐ прийнято |

## Завдання 3. Bridge (рецензент: Катя)

| Критерій | Що перевірено | Результат |
|---|---|---|
| Діаграма відповідає коду | `Report` (Abstraction) з `Channel`, три види звітів (Refined Abstraction), `IDeliveryChannel` (Implementor), чотири канали (Concrete Implementor) | ☐ |
| Рішення усуває проблему | Вид звіту й канал змінюються незалежно; будь-яке поєднання під час виконання (`report.Channel = ...`); новий вид або канал це один клас | ☐ |
| Раннер відтворює сценарій | Звіт про поїздку в застосунок і на e-mail; корпоративний звіт у бухгалтерію; канал Telegram-бот доданий одним класом і використаний для звіту про поїздку | ☐ |
| Додаткова перевірка | Цикл «усі звіти × усі канали» дає 12 повідомлень без нових класів | ☐ |

| № | Зауваження | Статус |
|---|---|---|
| 1 | `Channel` має публічний сеттер: це потрібно для зміни каналу під час виконання, але звіт стає змінним; у захисті пояснити | ☐ прийнято |
| 2 | Telegram-канал лише імітує доставку записом у журнал, реального API немає (вимоги забороняють сторонні бібліотеки) | ☐ прийнято |

## Підсумок

Діаграми відповідають коду, вимоги з описів ситуацій виконано, раннери відтворюють сценарії, кількість створених об'єктів виводиться. До захисту: підготувати відповіді на питання про різницю Flyweight / Composite / Bridge (див. розділ «Теорія» в гайді).
